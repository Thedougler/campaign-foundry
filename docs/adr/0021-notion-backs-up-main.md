# Notion backs up main; each page names the repo path it holds

GitHub issue [#48](https://github.com/Thedougler/campaign-foundry/issues/48).

GitHub stays the working copy and Notion holds a Backup of it: the Shattered Sea Wiki, the agent skills under `.agents/skills/` and every image in those trees. `.github/workflows/notion-backup.yml` runs `bun run cf -- backup` on each push to `main` that touches those paths, and on `workflow_dispatch` for the first full run. The Backup root is a new child of the Second Brain's "Shattered Sea (campaign)" page, so that page stays a short pointer. Each directory becomes a page and each file a page beneath it. A Backup copies, and it never feeds play: Push is still the only way material leaves the Wiki for the table, and nothing in Notion flows back into the repo.

Decisions:

- **A script in this repo, not nogisync.** nogisync finds pages by title through Notion search, which is eventually consistent and duplicates pages under same-named folders. It uploads no images and has no excludes, symlink handling or deletion. `cf backup` is about 1,400 lines of TypeScript on the official `@notionhq/client` (retries and Retry-After) and the remark stack the repo already uses.
- **Notion is the record of what exists; the map is a cache.** Every Backup page carries a marker from the request that creates it: the root its note, a folder page a first line naming its folder, a file page a header naming its repo path. Before a run plans anything it reads the Backup tree from Notion and repairs `.notion/backup-map.json` from it, so a missing, partial or stale map, or a page a stopped run made but never recorded, is adopted rather than made again. The root is looked for under the parent page and created only when none is there. A lost map costs one slow run (about 10 minutes on the full tree) and no new pages: the header names the commit the page was written at, so content hashes come back from git, and image upload ids come back from Notion's list of uploads by name and size.
- **Not `notion_page` frontmatter.** Writing page ids into frontmatter would make the workflow edit 400 Canon and skill files on its first run, put Notion URLs into pages the DM edits and the gate checks, and change skill frontmatter that harnesses parse. The markers live in Notion instead, and the map stays a committed cache: the workflow commits it back to `main` with `[skip ci]`, and `.notion/` is outside the trigger paths.
- **One page per path, never more.** If Notion ever holds two pages for one path, the run keeps the map's page (else a fully written one, else the oldest) and adds no other. An extra that is only an empty shell goes to Notion's trash, where it can be restored for 30 days. An extra with content is reported on every run and left alone, because trashing it would make Notion delete it for good after 30 days. Two runs at once can each create a page for a new path: after creating, a run looks again, and the run whose page is newer trashes its own empty copy and stops, so the rerun adopts the older one.
- **A page is complete only when its header names a commit.** A rewrite empties the page, writes a pending header and the body, then turns the header into the finished one. A page a cancelled run left half written keeps its pending header, so the next run rewrites it even with the map lost.
- **Two stages, one engine.** The first run creates every page empty, then writes content, so every `[[wikilink]]` already has a page to link to. Later pushes diff the map's `syncedCommit` to HEAD and touch only the files that changed. That base is the last commit fully in Notion, `HEAD^` on an ordinary push. A multi-commit push, a cancelled run or a failed run still reaches every change. A file with a recorded URL has its page content replaced in place. A new file gets a page. A deleted file's page is retitled "(deleted from repo)" and kept, never trashed, because Notion empties its trash after 30 days.
- **Safe to cancel.** The job runs in one `concurrency` group with `cancel-in-progress`. The map is saved after every Notion write and an `always()` step commits it, which keeps the next run fast; a page the cancelled run made but never recorded is adopted by its marker. `syncedCommit` advances only when a run ends with no failures.
- **Images through the File Upload API.** Each image is uploaded once, and a rebuilt map reuses the upload rather than sending it again. It is shown on its own page and reused by id wherever a page embeds it. The workflow checks out without LFS, and `cf backup` pulls only the LFS objects it uploads, keyed by the LFS object id (the content's sha256), to spare the LFS bandwidth quota.

The conversion's limits are listed in `docs/notion-backup.md`.
