# DDB homebrew writes go through captured contracts

GitHub issue [#45](https://github.com/Thedougler/campaign-foundry/issues/45). Amends the read side of [ADR 0009](0009-pcs-pulled-from-public-dndbeyond-characters.md): PCs come from public sheets, but homebrew must be *written* to D&D Beyond, and D&D Beyond publishes no supported write API. The DM's second-brain synthesis ["D&D Beyond homebrew agent integration"](https://www.notion.com/p/3f20216635ec81b3a9b6f9f02a4943a4) (Status: Current, reviewed 2026-10-06) is the research basis; [AlexWorland/dndbeyond-mcp](https://github.com/AlexWorland/dndbeyond-mcp) proves the auth path and [MrPrimate/ddb-importer](https://github.com/MrPrimate/ddb-importer) proves structured authenticated account mutations work.

The adapter is `src/ddb/` behind `cf ddb` (ADR 0007's rule: agents get a CLI, not raw internals). Agents hand it canonical JSON — the Wiki page's statblock fields, never D&D Beyond's payload shape — and it verifies every write by reading the object back.

- **Auth is dndbeyond-mcp's path, captured once.** The DM logs in through oh-my-pi's built-in browser (headed, persistent tab; the Chrome CDP relay serves when the DM prefers their real Chrome — chosen over a Playwright layer because the omp browser already owns headed login, cookie storage and request recording without a new dependency). Every `dndbeyond.com` cookie is saved to `~/.campaign-foundry/ddb-session.json` — user-level like dndbeyond-mcp's `~/.dndbeyond-mcp`, so it survives repo moves and serves every World. The long-lived `CobaltSession` cookie exchanges for a short-lived bearer token (cached until 30 s before its ttl); service hosts get the bearer, `*.dndbeyond.com` gets the full cookie jar besides, so the verification-token CSRF cookie rides along. A 401 is never retried: it means re-login.
- **Writes are captured contracts, not guesses.** dndbeyond-mcp's own audit shows guessed write routes 404. One DM-driven session per content type and operation records the site's own POST/PUT/PATCH/DELETE traffic (method, url, headers, body, status, response preview) while the DM edits one private homebrew monster. The capture is redacted — every cookie/authorization/token/csrf header value becomes `"<session>"` — and committed as a versioned fixture at `src/ddb/contracts/<type>/<op>.json`. The loader refuses a missing contract with the capture procedure and refuses an unredacted one outright, so nothing private can be committed and no write can run on a guessed route.
- **Transport order is direct HTTP, then the authenticated browser context.** `request()` tries direct HTTP with auth headers; on 403/429 (anti-bot, CSRF friction) it retries through the browser fetcher when one is wired; outside an omp session `cf` reports the remedy instead of failing opaque.
- **Every write is verified by read-back, never resubmitted blind.** `cf ddb verify` compares the canonical monster against what monster-service returns, field by field (name, size, ac, hp, hit dice, the six stats — the deterministic set; CR/alignment/type ids wait for the game-config endpoint mapping rather than guessing id tables). A mismatch is reported; the adapter never repairs or retries it, because a wrong write must stay visible.
- **Writes are gated.** `cf ddb replay <capture>` prints its plan and exits 2; only `--yes` reaches D&D Beyond, one request at a time in capture order, stopping at the first refusal. Test writes run only under the DM's permission: one at a time, an obvious `cf-test` name, deleted after verification. Replay re-fills redacted headers from the live session, so a committed capture never carries credentials that could go stale.

2026-10-07, the first full monster round-trip (create, verify, update, delete) landed and settled the open questions:

- **Create copies a base monster, exactly like the site's own form.** There is no JSON create: `POST /homebrew/creations/create-monster` (urlencoded) with the page's fresh `security-token`/`authenticity-token` hidden inputs, `monster-type` from the base monster's monster-service `typeId`, and the base id as `monster`; the `302` `Location` carries the new id. `cf ddb create --from <base-id> --file <canonical>` then saves the canonical fields onto the copy and verifies, so create = copy + update + verify.
- **Update posts the live-parsed builder form, never a baked body.** The builder at `/homebrew/creations/monsters/<id>-<slug>/edit` (slug from the monster-service record's url; it changes on rename) posts multipart with *every* control — wysiwyg pairs, empty fields, hashed ability names included. The adapter parses all `field-*` controls from the live edit page, overrides the canonical fields by field id, and posts the complete form; select values are matched by option label (the form's size ids differ from the old assumption — see below), so no id table is guessed.
- **Delete rides the creation page's own confirmation flow.** The view page's Delete link opens a modal (`GET /homebrew/creations/delete?entityTypeId=779871897&id=…`, XHR); confirming ajax-POSTs the same URL with the `RequestVerificationToken` cookie's value as the `request-verification-token` form field — that cookie must be in the saved jar (the first jar missed it). monster-service keeps serving deleted monsters from its CDN, so deletion is verified on the creation page: the edit/delete action links disappear.
- **The verify tables are live-probed, not assumed.** monster-service size ids run Tiny=2..Gargantuan=7 (Owl/Cat 2, Blood Hawk 3, Wolf 4, Brown Bear 5, Mammoth 6, Ancient Red Dragon 7) — the earlier Tiny=1..Gargantuan=6 table was off by one and had passed a verify only by coincidence. Hit dice normalize a trailing `+0`/`-0` on both sides, because DDB records `2d6` where the wiki writes `2d6 + 0`.
- **The write surface is three gated commands plus replay.** `cf ddb create|update|delete` each print their plan and exit 2; `--yes` performs them one request at a time, and each verifies what it wrote (create/update by read-back compare, delete by the creation-page oracle) before exiting 0. Contract drift is a named remedy: the committed contracts are versioned fixtures, and tests keep their URLs and body field names in lockstep with the adapter.

Contracts are reverse-engineered and can change silently. That is the accepted risk: verification catches drift at the field level, the browser fallback absorbs transport friction, and re-capture is a named remedy in every loader error.
