# The Combat sim is a seeded TypeScript engine that reads the Wiki

Umbrella [#90](https://github.com/Thedougler/campaign-foundry/issues/90) restores what Campaign-OS's JavaScript `combat-sim` and its Python successor `dndsim` could do, as parity of behaviour rather than of code. The coverage ledger in `docs/research/combat-sim-coverage.md` lists each legacy capability and the issue that owns it. This ADR fixes the design those issues build on.

Decision:

- **TypeScript on Node, inside `cfcli`.** The engine's code sits in `src/combat/` and runs as `cfcli combat <subcommand>`. It uses the repo's one toolchain, its Wiki parsers (`src/vault/` and the statblock fence parser) and vitest. The `dndsim` speed-up came from batching trials over NumPy arrays, not from Python ("D&D combat simulation performance: Python vs JavaScript" in the Second Brain). V8 runs a plain loop fast enough for the sample sizes adaptive sampling needs.
- **Trials run one by one.** A **Trial** is one fight played to its end on plain JavaScript objects, and the engine plays each Trial separately rather than stepping many of them together through shared arrays (legacy ADR-0011), since that design forces each mechanic into a second, masked form. Independent work spreads over a `worker_threads` pool once one thread is too slow for it.
- **Seeded and reproducible.** Random draws come from a seeded PRNG (`pure-rand`). A Trial's stream depends only on the run seed and the Trial's index. The result replays bit-identically at any worker count. A run records its engine version (git commit), seed, input page paths with content hashes, Scenario and command.
- **The Wiki is canon for the engine's input, kept as structured data Obsidian renders.** Creatures and NPCs compile from the `statblock` fence under their page's `## Statblock` (ADR 0044). A PC's `## Sheet` gains the same Fantasy Statblocks fence with its numbers, its features as traits and its attacks in statblock grammar. One Importer then reads PCs, NPCs and Creatures alike, and Obsidian renders a PC's numbers as it renders a monster's. `pull-pcs` fills that fence from D&D Beyond when a character is public. The engine never reads D&D Beyond. A private character plays from its page, and agents keep its fence by `statblock-design`. Combat House Rules and Scenarios sit on their pages as frontmatter properties or fenced YAML. When the engine needs a fact a page lacks, the page's template gains a structured place for it, and the skill that writes that page learns to fill it.
- **Importers compile content to Primitives.** An **Importer** turns a page into a **Combatant**, which holds numbers plus Actions built from a closed vocabulary of **Primitives** such as attacks and saves. Importers read both 2014 and 2024 statblock grammar. A feature that compiles to no Primitive becomes an **Unmodelled feature** on the Combatant. Reports list it by name instead of dropping it.
- **A rule has one home.** Each Primitive has one **Mechanic** module in `src/combat/rules/`. It resolves the Primitive during a Trial and gives its expected value to the Policy, and a test checks the two agree (legacy ADR-0008). Parsers, Policies and reports call the Mechanic and don't copy its rule (legacy ADR-0007's forcing case). The engine plays the 2024 rules. It has no rules-pack plugin layer, because the Campaign plays one edition and House Rules are named options on it.
- **Policies are swappable.** A **Policy** chooses each Combatant's action, movement and targets from the options its resources allow. Each side has its own Policy. The default is greedy expected value with focus fire. Forced routines and the other targeting priorities plug in behind the same interface (#97).
- **Space is approximate.** Positions are a coarse geometry that #96 builds. Before #96 merges, the engine treats each enemy as within each Combatant's range, and the run's provenance states that assumption.
- **Commands.** `cfcli combat compile <page…>` compiles pages and reports each Combatant with its Unmodelled features. `cfcli combat run` plays a Scenario and reports outcomes. Later issues add `profile`, `sweep`, `tune` and `observe` under the same command, with the same Scenario input and provenance.

Consequences: the simulator builds and tests like the rest of `cfcli`. Its inputs are pages agents already write, and better pages give better results. A Combat sim result is evidence for the DM and never edits a page itself: tuned variants wait for review (#101), and observed table results stay apart from simulated ones (#103). #94 measures throughput against real Shattered Sea Combatants, and the worker pool arrives with the first issue whose workload needs it.
