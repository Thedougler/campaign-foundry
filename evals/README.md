# Shattered Sea skill evals

This document is the eval case contract. It defines the terms and the Design every committed case meets, the standing Wiki agreement criterion, the safety and pass rule of every run, and the grounding of its inputs. Read it before authoring, changing or grading a case or criterion. The procedures are in skills:

- **Design** a suite using [Design](#design) before a suite measures a content skill, whenever a criterion proves broken and whenever the DM's intent changes.
- **Run, measure or improve** a skill or process with `skill://dogfood`, the route for every change to agent-facing text (ADR 0034). Its `references/evals.md` runs cases and holds the weekly feedback loop. A DM-started run is the only branch that adds eval cases to an existing skill (root `AGENTS.md` **Skill verification**).
- **Create** a skill with `skill://skill-creator`, which drafts a new content skill's default case.
- **Benchmark** Narration with `skill://dnd-benchmark`, on DM request. A blind Council's Grades from 1 to 5 and rankings order models, separate from skill pass/fail (ADR 0038).

Runners and graders are native `task` dispatches of read-only agents. Description trigger checks are read-only `omp -p` processes launched from Bash ([Safety](#safety), ADR 0016).

## Terms

Each term is defined here once. Skills and instruction files use these terms.

- **Sample** is a DM ask taken from production: a home-Session report, a GitHub issue or a recovered DM ask.
- **Default case** is the one case for a content skill's content type in its `evals/cases.yaml`. It is a Sample asking for a complete piece of that type. Its rubrics together define professional-quality content of that type, including Narration (ADR 0017). It passes only when every criterion holds.
- **Runner** is the `test-subject` dispatch, or `smart-test-subject` for a case marked `subject: smart`, that performs a case's DM ask from the skill, the template, `campaign-config.md` and the case's listed sources alone, and returns its pages and DM reply as its result. It returns each page as written and doesn't run the gate (ADR 0037).
- **Outcome** is `createOutcome(vault, outputRoot)` in `evals/check.ts`. It overlays the run's `$out/outputs` pages on the live Wiki pages and hides live pages whose deletion the run recorded. It also includes `reply.md`, the DM reply. Checks and Grades judge the Outcome, not the tool-call path.
- **Check** is `bun evals/check.ts` (pages, sections, canon/absent regex) on a constrained Outcome: a page the run itself returned (a live page the Runner left untouched fails `pages`), `type: Handout`, text the Runner must leave untouched. A page key holding `*` names every page the run wrote that matches it, for an ask that leaves the filename to the Runner (`bun evals/check.ts --help`). The same invocation runs the gate's `statblock` layer read-only over the run's output pages to check rules arithmetic. A statblock error fails the case like a Check failure, and a warning is reported (`WARN`) and passes (ADR 0015). Evals measure no prose lint (style, narration), which `skill://dogfood` observes in live production units (ADR 0037). Checks are the cheapest grader.
- **Grade** means a grader reads the writing and quotes it. Each rubric is a checkable claim about meaning and intent: does the table get the situation? This is creative writing, so no rubric requires verbatim wording, and copying a source's prose is a weakness rather than fidelity. "Intact" or "kept" means sections, facts and callout titles, not whitespace or formatting. Skill-eval Grades are pass/fail, from `prose-grader` on a model outside every model under test (`.omp/AGENTS.md` **Model choice**). Benchmark Grades are a Council's scores from 1 to 5 and rankings, from the models under test themselves (ADR 0038). Grades score skills. The File gate is deterministic (ADR 0010).
- **Jev** (`judge` / `judge_batch` in `eval`) means bounded labels over a small state. It is not a Grade of Narration.
- **Baseline run** is a Runner run of a case without the skill line (`skill://dogfood` `references/evals.md` step 1).
- **Eval** means running selected cases per `skill://dogfood` `references/evals.md`. Each case gets one with-skill Runner against the read-only live Wiki, then its Checks and Grades, and that one run decides each criterion's verdict. A run leaves skill text unchanged.
- **Benchmark** is the requested blind Council ranking of Matrix families on one DM-written Benchmark prompt (ADR 0038), separate from skill pass/fail.
- **Playtest** is the weekly home Session: production monitoring that feeds Sample and never replaces Eval.

## Design

Criteria codify the DM's intent and steer the project's development (root `AGENTS.md`), so every case and criterion serves better Sessions. A wrong criterion wastes the time and tokens of every run it grades: rework or retire a case or criterion that does not serve that goal, and fix one that contradicts it.

Apply to a content skill's committed `evals/cases.yaml` before a `dogfood` run uses its cases. Record each case's one-line verdict in the `#` comment above it.

An eval case isolates one desired behaviour and confirms that the skill performs it reliably. Rounds then iterate on it quickly and cheaply (ADR 0035). Every case meets these rules:

- **Isolate.** Each case confirms one behaviour through one natural DM ask. The ask may bundle facets, as the default case does for a complete piece of its type. A prompt combining two separate DM asks, or an unrealistic one, becomes one case per realistic ask. The new case ids come from a DM-started `dogfood` run (root `AGENTS.md` **Skill verification**). Each criterion judges one behaviour pass/fail. A flipped criterion then points to the behaviour that moved.
- **Plain ask.** The prompt is the DM's request in the DM's words. It gives the target page and the concrete situation, plus the facts the ask needs, never "whatever X leaves us with". What the answer should contain or avoid (sections, callouts, steps, wording) is written in Checks and rubrics, which the Runner never sees ([Safety](#safety)). A prompt that coaches the answer measures the prompt rather than the skill.
- **Tight scope.** `source_pages` list exactly the pages the ask needs: the target page, each page the prompt mentions and each page holding a fact a criterion judges. The Runner reads all of them and nothing else, so a missing fact is a case defect and an unneeded page is a wasted read: repair either here. When [Wiki agreement](#wiki-agreement) fails on a page outside `source_pages`, add that page when the ask depends on its subject. Otherwise the Runner asserted facts about a subject it never read, and the failure stands.
- **Efficient iteration.** Checks decide every constraint a rule can verify, with no model call and the same verdict every run. Rubrics judge the remaining craft. One run decides each verdict ([Terms](#terms) **Eval**): with one behaviour per criterion, a real skill effect shows as a visible flip. A case, source page or criterion stays only when its value covers the Runner and grader cost it adds. Avoidable token and time cost is friction (`skill://dogfood` step 3).

1. **Default case.** The suite contains one default case. It is a natural DM ask for a complete piece of the content type with current Shattered Sea `source_pages` / `raw_sources` (see Grounding). Its rubrics state professional quality for the type as a DM running it at a real Session reads it: specific rather than generic, alive and dramatic, table-ready, and Narration slots that meet `theatre-of-the-mind`. Consistency with Canon is graded by [Wiki agreement](#wiki-agreement). Where the product is rules (a Creature's statblock, a Spell), one secondary criterion sets the rules floor: correct, complete and easy to run at the table under the 2024 rules. Other types have no rules criterion. Done when the case exercises every part of the type's template and its rubrics cover each quality.
2. **Extra cases.** Add a case only for a unique circumstance the default case cannot expose, such as chat-only delivery, a Handout or revising a whole Session's Narration, or for an ask split out under **Isolate**. Put a one-line `#` comment above it stating the circumstance. A suite may also contain one adversarial case. Mark it as adversarial in its `#` comment. Its prompt pushes the skill toward a known defect: quietly rewriting established Canon, lore-dump delivery, a predetermined ending or a single-Clue dependency. The rubrics pass when the skill refuses or redesigns the request, or offers its own alternative in the skill's terms. Trigger accuracy belongs to description evals in `skill-creator`, DM-gated. Done when every extra case has its comment and no case repeats what the default case covers.
3. **Grader.** Checks own everything code can decide, the `statblock` layer's arithmetic included. Rubrics own only the creative quality no linter can judge: the craft that makes professional-grade table content, in claims two DMs would decide alike from the same starting Wiki. A rubric that grades prose lint (style, AI tells, wording a lint rule flags) or restates a Check is defective: cut it, or move a constraint code can decide to `checks`. We grade intent, not exact wording. Checks pin structure (a page, `type:`, a callout title) and text the Runner must leave untouched, and never the wording of what the Runner writes. Rubrics name facts and craft, so a Runner-chosen filename, a reworded line or a paraphrased source fact passes. Cut any rubric clause that restates [Wiki agreement](#wiki-agreement) in general terms, and keep the case facts it names, the ones most at risk in this ask. A criterion that fails content meeting it is broken: repair it here. Done when every criterion judges one behaviour and sits on the right side of the Check/Grade split.

**Done when** steps 1 to 3 hold for every case. A case that a baseline run passes outright is hardened in `dogfood`'s optional Optimise phase (`references/optimise.md`). Evals exist for skills that create professional-grade D&D content, and their criteria grade creative writing and that content's quality first. Everything else is secondary. Process and tool skills have no evals or rubrics.

## Wiki agreement

Campaign content never contradicts the Wiki (DM, 2026-10-11). Every case that lists `source_pages` is graded on this standing criterion as well as its rubrics, and no case names it. The `dogfood` recipe appends it to the grade brief (`references/evals.md` step 4), and the grader checks it against the whole live Wiki, reading further pages beyond the case's sources (`.omp/agents/prose-grader.md`). The criterion, verbatim:

```text
Wiki agreement: every claim the Outcome makes about an existing subject agrees with the starting Wiki or changes it as Canon allows. Canon precedence settles a conflict (CONTEXT.md **Canon**): the DM's words in the ask, then the Wiki, with fixed Canon over draft Canon. A page whose `revealed` is set is fixed Canon, and a change to it only adds depth, history, consequences or new facts, leaving everything revealed standing. A page with `revealed: ""` is draft Canon, and a page the run returns may reflavour it when every other Wiki page still agrees with the new version. Prep, plans and proposed outcomes stated as played history contradict the Session records. New material where the Wiki is silent agrees.
```

## Safety

Eval processes read the live Wiki and cannot change it:

- **Runners and graders** are native `task` dispatches of `test-subject` (or `smart-test-subject`) and `prose-grader`, whose frontmatter `tools:` is read-only except the Runner's `bash`: `read`, `grep`, `glob` for the grader, `read` and `bash` for the Runner. The Runner's `bash` runs read-only diagnostic CLI such as `cfcli encounter-budget`, and writes the Runner's page drafts into one `mktemp -d` directory beneath `$TMPDIR`. Checks run over those pages afterwards (`skill://dogfood` `references/evals.md` step 3). A dispatch also gets `yield`, `context_notes`, `new_context` and a `write` that reaches only `xd://` devices, which cannot write files, and it receives neither DM decision memory nor `manage_skill`.
- **Benchmark Runners and Council graders** are native `task` dispatches of `bench-runner-<family>` and `bench-grader-<family>`, whose `tools:` grant `read` and `web_search` with the Notion Backup's read tools and QMD search. Their definitions limit them to the Benchmark prompt and its craft files, the Backup, the inspired-by cache and the web (`skill://dnd-benchmark`).
- **CLI processes** (description trigger checks, `skill://skill-creator`) run `omp -p` from Bash. `--tools read,grep,glob…` brings the same `xd://`-only `write`, and `--no-tools` brings none. `--config evals/subject.config.yml` turns DM decision memory and autolearn off. Runs do not see or feed DM memory. These processes run without `manage_skill`.
- QMD search, for eval authoring ([Grounding](#grounding)), runs through the `xd://` devices: `write` JSON to `xd://mcp__qmd_query` and `xd://mcp__qmd_get` (`read xd://mcp__qmd_query` for the schema), over the existing live index. Runners do not search. Eval work never copies or rebuilds an index.

Answer isolation removes the criteria from everything the Runner receives. No dispatch `context` or `task` contains a criterion, and the rubrics go to the grader alone. The Runner's `read` and `bash` could still open `evals/`. Its definition, `.omp/agents/test-subject.md`, tells it to open only the files its reads list and to leave the rest of every `evals/` folder unused. A fixture its `Sources:` lines name counts as a listed file. Case files and rubrics stay unread. Each run still ends with the cleanliness check in `skill://dogfood` `references/evals.md` § Concurrency and cleanliness.

## Pass rule

A case passes when Checks exit 0 and `grades.json` parses with one entry per graded criterion, every `pass` true. The graded criteria are the case's rubrics, then [Wiki agreement](#wiki-agreement) when it lists `source_pages`. A case with neither needs Checks alone. Classify every other case:

- **Quality failure** means Checks exit 1, or a grade with `pass: false`.
- **Execution error** means the Runner failed or timed out, the Runner did not return a result, or Checks exit 2.
- **Grading error**: the grader failed, or `grades.json` is invalid. Invalid means it is not the specified JSON, is missing a rubric or contains `{"error":…}`.

Errors are named prerequisites: neither quality failures nor passes. The suite score is the fraction of selected cases that pass. Report model identity, thinking and cost (tokens, tool calls, wall time) only where observed. Each Runner runs `test-subject`, on the test-subject model `.omp/AGENTS.md` **Model choice** sets, unless its case is marked `subject: smart`. That case runs on `smart-test-subject` (`@SMART-TEST-SUBJECT`), because its failures showed the weak Runner's gap is intelligence rather than unclear text (`skill://dogfood` step 5 decides when to mark it). A provider fallback that substitutes the Runner's or grader's model mid-run is a divergence, and the affected run is rerun on its assigned model.

## Grounding

The DM's weekly home Sessions playtest the Wiki and the skills that produce it. **The Shattered Sea** World and its **Shattered Sea** Campaign are the input source for every active skill eval: committed cases and Narration benchmark prompts. A case whose circumstance is output tied to no World, such as a reusable monster, doesn't list `source_pages` and says so in its `#` comment. The Agent works between Sessions. The DM and Players supply table evidence.

When authoring or changing eval inputs, search the Wiki (`.omp/AGENTS.md` § Wiki access) and read the hits, then read the Campaign's `hot.md`, World `index.md`, available last ten `log.md` entries and source pages. Read current templates for output shape. Canon comes from the Wiki. Raw and Archive establish provenance. Distinguish played events from Prep, missing information from established facts, and requested new output from existing Canon. In a run the Runner reads the skill, the template, `campaign-config.md` and the case's listed sources, then writes, without searching (`.omp/agents/test-subject.md`). For evals only, this replaces the earlier practice of Runners searching the Wiki as production does. Production agents still search. Cases ask about pages as they currently stand; Grades judge changing facts and quotations against the live sources, not cached factual literals.

Each committed case records:

- `source_pages`: existing Wiki-relative Shattered Sea pages, scoped as [Design](#design) **Tight scope** sets. The grader reads them as the truth, with any further live page it checks for [Wiki agreement](#wiki-agreement), and the Runner reads them as its whole research.
- `raw_sources`, when the ask concerns Raw or Archive material: existing repo-relative live `raw/` or `archive/` inputs.
- `fixtures`, when the ask builds on an outside work the DM names: repo-relative files under the skill's `evals/fixtures/`. Each one is a byte copy of the researched note for that work (`.cache/inspired-by/<slug>.md`, root `AGENTS.md` **Sourcing**), with its sources, fetch date and *(unconfirmed)* marks as they were, and the case's `#` comment names the file it was copied from. The Runner reads it in place of the cache lookup and web research, and the grader reads it as the truth about that work. The gates leave fixtures unlinted.
- `prompt`, deterministic `checks` and independent `rubrics`: a natural DM ask and private criteria for observable behavior grounded in those inputs.

Migrate still-useful criteria to real sources as you go. A reported issue adds a criterion. It does not add a case unless it is a unique circumstance. Synthetic Worlds, invented Transcripts and hand-written replacement source pages are not skill-eval inputs. Software unit-test fixtures remain separate. Historical eval artifacts remain unchanged, and historical `docs/intent/**/evals/evals.json` is intent, not an executable input source.

Use recovered production asks where available. Keep the DM's intent and table facts and add nothing else ([Design](#design) **Plain ask**). The Runner task contains the skill line, the ask and its `Sources:` lines, and `.omp/agents/test-subject.md` supplies the read recipe. Keep useful grounded adaptations labelled as adaptations: source provenance is not proof that a creation request was recovered.

House Rule coverage ingests the recovered Archive Mortis (`archive/mortis.md`, `archive/mortis-dm-guide.md`). An Ingest case specifies its live `archive/` input in the ask, and the Runner returns the resulting pages. If a case's ask is a grounded adaptation rather than a recovered DM ask, state that in its `#` comment. Successor-Campaign and `pull-pcs` `public-sheets` use the four public D&D Beyond URLs on the existing PC pages. Original PC-creation asks remain unrecovered.
