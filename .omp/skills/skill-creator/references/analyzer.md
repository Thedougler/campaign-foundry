# Evidence diagnosis

Read when the DM requests explanation of paired results or a blind comparison. The parent may analyze the saved evidence directly or brief a fresh native `prose-grader` with the analysis contract below. Use the existing configured role; this reference does not define another native agent. `evals/README.md` owns access and lifetime, `eval-loop.md` owns pair admission, and [`schemas.md`](schemas.md) owns `analysis.json`.

## Parent brief

Name the question: explain a specific output difference, or surface patterns hidden by aggregate results. Supply the relevant saved outputs, frozen starting inputs, Grade artifacts, complete histories, skill versions, benchmark data and evidenced pair-admission/exclusion decisions. When comparing, include `comparison.json` and the previously private A/B mapping; a `tie` remains a tie. Sources belong to the measured run, not current live Canon.

For delegated analysis, dispatch a fresh native `prose-grader` with a strict `outputSchema` for `{observations,instruction_following,improvement_suggestions,limitations}` as defined in `schemas.md`. State explicitly that this is evidence diagnosis, not pass/fail grading or Benchmark scoring. The grader yields the structured result; the parent validates and saves `analysis.json`. For parent analysis, use that same artifact shape. Done when the question, saved evidence paths and structured result contract are explicit.

## Analysis steps

1. **Bound the evidence.** Read the saved pair decisions, Grade/comparison results, outputs and required starting inputs. Separate comparable pairs from excluded/error runs; excluded runs can explain harness failures but cannot establish a skill advantage. Record missing histories, unobserved metrics, small samples and absent source evidence as limitations. Done when every analyzed result has an identified scope and prerequisites, or the missing required material is reported as a blocker.
2. **Find the distinction.** For output diagnosis, quote the passages behind the relevant Grade or winner/tie conclusion, then trace relevant skill instructions and observed history calls. A history shows actions, not hidden reasoning. For aggregate interpretation, identify which eval IDs, run numbers and verbatim expectations exhibit the pattern; use observed metric fields only. Done when every observation cites exact output/source text or saved result fields and names the runs to which it applies.
3. **Explain or limit.** Distinguish observed behavior from a causal hypothesis. Tie a proposed process change to the instruction, observed action and consumer-visible defect it would address. Label uncertain causation explicitly; an output difference alone does not prove its cause. For an aggregate-only question, keep unsupported diagnosis/suggestion arrays empty rather than inventing improvements. Done when each explanation has a cited evidence chain and every unsupported claim is removed or identified as a limitation.
4. **Yield and map.** Return the declared structured result; observations include their evidence and scope, instruction-following findings cite instructions and observed behavior, and suggestions carry priority, category, concrete change, evidence and expected impact. Instruction following is described with quotations, not numeric scores. The parent validates and saves the result unchanged as `analysis.json`, adding the separate native completion/provenance evidence when delegated. Done when every populated field is traceable to saved artifacts and the result preserves ties, exclusions and unavailable evidence.

Leave the measured writing, skill versions, criteria, Grades, comparison decisions and benchmark metrics unchanged. Revisions are a subsequent `skill-writer` assignment based on the accepted analysis, not work performed by the diagnosis role.
