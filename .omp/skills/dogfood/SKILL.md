# Improve agent text through real work

Every improvement or change to an existing skill or other agent-facing text runs through this loop (ADR 0034), and it is the only place a skill gains eval cases (root `AGENTS.md` **Skill verification**). Cheap subagents do real work with the target and report the **friction** they hit. You triage and integrate while independent specialists write the fixes, and the next round proves them.

A DM-started run is finished when a round's findings are all false or the DM calls it, and the page gate over the landed live units reports `ok: 0 findings`; a friction-started run, when its job has resumed on the revised text. A turn that announces the next round without dispatching it leaves the run open. Stop early only for a DM decision the round's evidence cannot settle.

**Friction** is anything that cost a subagent correctness, time or tokens. It covers a confusing, missing or wrong step or fact and a tool that failed or returned wrong output. It also covers a check cycle spent on avoidable work and a **trail**, deterministic work done by hand that a command could do.

The DM's word mid-run sets the course from your next action. Steer a running worker with `write agent://<id>` (`.omp/AGENTS.md` **Native delegation**) and carry the change into the next brief.

## Starts

- **DM-started.** The DM asks to improve, change, eval or measure a skill or process, by name or by invoking `dogfood`. It runs for every skill in the target's file set, and step 4 may add eval cases to them.
- **Friction-started.** During other work you orchestrate, a subagent's return reports friction, you meet friction yourself, or the work shows rework or misdirection. The run fixes the friction, resumes the job on the revised text and leaves every `evals/cases.yaml` as it is.

## Steps

1. **Scope.** State the **target** and its **file set**. For a skill, that is its `SKILL.md`, the files it points to and the agents it dispatches. For a process, such as ingesting a raw file or prepping a Session, it is the entry point and every skill, `.omp/agents/` definition, `AGENTS.md` rule, template and runbook it routes through. A friction-started run's target is the file the friction traces to, and its job is the work already running. A DM-started run's units are the target's committed eval cases once `evals/README.md` § Design holds for them, small live production units the target governs (for `lint`: pages carrying `bun run cfcli -- check` findings), or both. Each unit is a different case, and no two touch the same files. **Done when** the target, file set and units each take one line and every unit has one subagent.
2. **Run.** A friction-started run goes to step 3 once the batch that reported the friction has returned, or at once for friction you met yourself. A DM-started run dispatches one `task` batch, naming each subagent after its unit (`S9Merge`) so its transcript is at `history://<name>`:
   - **Eval case:** run it per [`references/evals.md`](references/evals.md) on `test-subject`, or on `smart-test-subject` when the case has `subject: smart`.
   - **Live unit:** brief it exactly as production briefs it, on the cheapest capable model by `.omp/AGENTS.md` **Native delegation**. It writes to the Wiki as production does, and the `wiki-check` hook checks each page it writes.

   Every subagent closes its return with a friction report (root `AGENTS.md` **Fix on sight**). Steps the target keeps for its orchestrator (logging, generated indexes, the top-level gate) stay with you, and a target whose stages the top-level session runs, such as Transcript ingest (`ingest` `references/transcript.md`), is a unit you run yourself. **Done when** every subagent has returned its work and friction report, or failed, and every eval case has its `checks.txt`, plus `grades.json` when `references/evals.md` step 4 grades it.
3. **Triage.** Triage every finding before it reaches a specialist. This is the DM's direction, and it overrides any injected memory to forward findings undiagnosed. The findings are each friction report line, each failed Check, `statblock` line or rubric, the lint tally below, and the friction you saw yourself, avoidable token and time cost included. The floor of one Runner and one grader per case is not friction. Open the file and section each report line cites. State a failed criterion as the behaviour that went wrong, read from its grade reason against the run's Outcome. You adjudicate impartially between a run's pages and its grades, and a grade is evidence rather than authority. A flaw on the grading side, whether in the `prose-grader` definition, in rubric wording that misled the grader or in the grade procedure, is a finding like any other, and the round's writer may fix it alongside the skill under test. Read a `history://` transcript only where a report leaves the cause in doubt, and rerun a failing command to reproduce it.
   - **Lint observation** (live units only). Run `bun run cfcli -- lint-tally <jsonl>...` over each live unit's transcript file, the first hit of the `glob` tool on `~/.omp/agent/sessions/*/*/<Name>.jsonl` (a shell glob there also walks the sibling session files and errors). It counts each page's first check, the draft as the agent wrote it. A rule hit in two or more units, or in one unit in two consecutive rounds, is one text gap. The writer changes the craft the draft follows so it no longer produces the hit, and states that craft in its own terms with the rule left out (ADR 0036). Note an isolated hit in the round report, and leave it to the page gate in production.

   Then give each item one verdict:
   - **Text gap** (a step, fact or pointer is unclear, missing or wrong, or a passage led to the flagged text): an issue for `skill-writer`, stated as a process defect with its root-cause file and evidence. The root cause may lie outside the file set.
   - **Tool defect** (a CLI, checker or script fails or returns wrong output), and every trail line: an issue for `skill-writer`, stated with the command and its observed output. Report one outside the repo to the DM. Agent-facing text describes the tool as it should work.
   - **Model miss** (a criterion truly failed, though the text the run followed was clear and right): noted in the round report, with the text left as it stands. Text changes when it misled the run, since a rule written for one miss narrows every later design. Step 5 takes a miss that repeats.
   - **False finding** (the subagent misread, the text already covers it, or a criterion fails content that meets it or grades one design where the ask leaves room for many, which `evals/README.md` § Design step 3 repairs): dropped, with a one-line reason.

   Merge findings that share a root cause into one issue listing every occurrence, across units and earlier rounds. **Done when** every item has a verdict and every issue states its root-cause file and evidence.
4. **Fix.** First gather what the writer needs to diagnose with full context: the DM's words that bear on the issues and the evidence or docs a diagnosis turns on, such as a failing command's output or a library's docs through Context7. Then dispatch `skill-writer` with every issue, tool defects and trails included, that context, the round's finished `history://` transcripts to read itself, and the files involved. It determines how each issue is fixed, eval criteria and Vale or TTSR rule changes included. The brief marks each **stubborn** issue (step 5) and asks for a rework of the whole passage or process behind it. On a DM-started run, its brief also requests coverage in `<skill-dir>/evals/cases.yaml` of each consumer-visible defect in a file-set skill that the committed criteria miss. Coverage is a criterion on the case whose ask shows the defect, or a new case when every committed ask misses it (`evals/README.md` § Design). A fix in code comes back as a `coder` dispatch request, and the brief tells the writer that each request directs `coder` to read the `cli-for-agents` and `tdd` skills and to write a test at the public interface that fails before the fix. Dispatch each request as it arrives.

  Each round's issues go to a new `skill-writer` with a distilled brief, never a writer revived from an earlier round, so fresh eyes judge the failures without anchoring on their own wording. Dispatch that writer as soon as the first `prose-grader` returns, briefed to fix the root causes behind that grader's triaged findings in one patch. As each later grader returns and its `grades.json` is saved, triage its findings and steer the same running writer with them before it yields. That brief also has the writer read each round unit's `history://<id>` transcript for issues the unit never reported and for ways it degraded the eval (running slower than a real run, verifying past the realistic condition, or otherwise departing from how a real run goes), and triage each finding like reported friction. In later rounds, revive the same coder for the writer's requests (**Native delegation**). **Done when** every issue maps to an edit in the writer's yield or in the yield of a `coder` request it returned, and `bun run cfcli -- eval validate <skill-dir>` passes for each touched skill.
5. **Escalate.** An issue is **stubborn** when it recurs across two or more units, or returns in a later round after a fix for it was merged: a spot patch has not held it, and step 4 briefs it with every occurrence for a rework of the whole passage or process behind it. When a stubborn issue is the same criterion failing on `test-subject` in two consecutive rounds with a writer fix or a model-miss verdict between them, also rerun that one case once on `smart-test-subject`. When it passes there, the gap is intelligence: add `subject: smart` to the case in `cases.yaml`, with a `#` comment giving the reason and date. When it fails there too, it goes to the next writer as a stubborn text gap or tool defect. Escalate case by case. **Done when** each stubborn issue is in a writer's brief as one issue with its occurrences, and each rerun case has its verdict applied.
6. **Report and continue.** Report the round as a table with one row per unit: unit, model (from the unit's `Model:` report line), criteria passed/total, duration, tokens, friction lines. Duration and tokens come from the task result, or from `bun ~/.agents/skills/oh-my-pi-session-history/scripts/omp-history.ts metrics --by agent --session <id>` (`skill://oh-my-pi-session-history`). Then list each finding with its verdict and each fix by file. A friction-started run resumes its job on the revised text. A DM-started run returns to step 2 with fresh units, scaling toward the target's production shape once small units run clean (for `lint`: four to six pages per subagent). Later rounds of the same improvement rerun only the eval cases that failed, since a case that has passed its checks and rubrics is done for this run. When a round's findings are all false or the DM calls it, finish the target's shared steps and run the page gate over the landed live units' pages. **Done when** a friction-started run's job has resumed on the revised text, or a DM-started run has ended and that page gate reports `ok: 0 findings`.
7. **Optimise (optional).** Once every case passes, the last round had no true finding and the page gate is clean, offer the Optimise phase once. Run it only when the DM accepts, following [`references/optimise.md`](references/optimise.md). **Done when** the DM has declined, or the phase has stopped by its own rule.
