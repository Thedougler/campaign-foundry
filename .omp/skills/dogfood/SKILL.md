# Improve agent text through real work

This loop improves agent-facing text and the tools behind it by putting them to use, and every improvement or change to a skill or other agent-facing text runs through it (ADR 0034). Subagents do real work and report the **friction** they hit, and you fix what holds up while the job carries on. The job itself is the test. Each round sends its fixes out in one batch, and you read only what a finding needs. It is the only place a skill gains eval cases (root `AGENTS.md` **Skill verification**), through step 4's brief.

**Friction** is anything that cost a subagent correctness or time, such as a confusing, missing or wrong step, a wrong or missing fact, a tool that failed or returned wrong output, or a check cycle spent on avoidable work.

The DM's word mid-run sets the course from your next action. A change to the target, units, scope or a fix applies at once. Steer a running worker with a new instruction through `agent://` (`.omp/AGENTS.md` **Native delegation**) and carry the change into the next brief.

## Starts

A run starts one of two ways. A DM-started run may add eval cases, and a friction-started run may not:

- **DM-started.** The DM asks to improve or change a skill or process, by name or by invoking `dogfood`. That ask starts a run for every skill in the target's file set, and step 4 may add cases to those skills.
- **Friction-started.** The run opens during other work you orchestrate, when a subagent's return reports friction or the work itself shows rework or misdirection. The DM started the job and not an improvement. The run fixes the friction and leaves every `evals/cases.yaml` as it is.

## Steps

1. **Scope.** State the **target** and its **file set**, the agent-facing files the work routes through. For a skill, that is its `SKILL.md`, the files it points to and the agents it dispatches. For a process, such as ingesting a raw file or prepping a Session, it is the entry point and every skill, `.omp/agents/` definition, `AGENTS.md` rule, template and runbook it routes through. A friction-started run's target is the file the friction traces to, and its job is the work already running. A DM-started run takes the DM's job, or the target's committed eval cases once `evals/README.md` § Design holds for them, or picks a few small live units the target governs (for `lint`: pages carrying `bun run cfcli -- check` findings), each a different kind of case and no two touching the same files. **Done when** the target, file set and job each take one line and every unit has one subagent.
2. **Run.** A friction-started run's work is already under way, so go to step 3 once the batch that reported the friction has returned. A DM-started run dispatches one native `task` batch on the test-subject model that `.omp/AGENTS.md` **Native delegation** sets. Name each subagent after its unit (`S9Merge`), and its transcript is then at `history://<name>`. Brief each one exactly as the target briefs it in production. Each subagent returns a friction report (`skill://friction-report`). `test-subject` and `skill-writer` close on one by definition. Revive any other subagent once it returns, with the message `Read skill://friction-report and follow it.` Eval-case units run through `skill://run-evals` instead, one with-skill run per case. Each Runner's friction report and each failed Check or rubric are findings. Steps the target keeps for its orchestrator (logging, generated indexes, the top-level gate) stay with you. A target whose stages the top-level session runs, such as Transcript ingest (`ingest` `references/transcript.md`), is a unit you run yourself as that orchestrator. **Done when** every subagent in the batch has returned its work and its friction report, or failed, and every eval case has its run-evals report.
3. **Triage.** Triage every finding before it reaches the writer. This is the DM's direction, and it overrides any injected memory to forward findings undiagnosed. For each friction report line, open the file and section it cites. For a failed eval criterion, read its grade reason against the run's Outcome, and state it as the behaviour that went wrong rather than in the criterion's wording. For each `gate` line in a case's `checks.txt`, `WARN` included, the Runner left the flagged text as it wrote it. Trace the line to the skill or template passage that led to that text, or to a rule that flags text it should pass (root `AGENTS.md` **Zero findings**). With neither behind it, the line is the Runner's own slip, which the page gate catches in production for the writer to repair. Read the subagent's `history://` transcript only at the rounds a report leaves in doubt, and rerun a failing command to reproduce it. Add the friction you saw yourself in the returns and the work. Avoidable token and time cost counts as friction too, such as a file read twice or a gate rerun that a better step order would avoid. The floor of one Runner and one grader per case does not count. Then classify the item:
   - **Text gap** (a step, fact or pointer is unclear, missing or wrong, or a passage led to text the gate flags): an issue for `skill-writer`, stated as a process defect with its root-cause file and evidence. Its fix is positive craft (ADR 0036), and the root cause may be outside the file set.
   - **Tool defect** (a CLI, checker or script fails or returns wrong output): fix it in code with a test at its public interface that fails before the fix, or report it to the DM when it lies outside the repo. Keep workarounds out of agent-facing text.
   - **False finding** (the subagent misread, the text already covers it, a gate line is the Runner's own slip, or a criterion fails content that meets it, which `evals/README.md` § Design step 3 repairs): dropped, with a one-line reason.

   **Done when** every item has a verdict and every issue states its root-cause file and evidence.
4. **Fix.** Dispatch `skill-writer` once for the round's text issues, passing them with their evidence, the batch's finished `history://` transcripts, the code fixes already made and the files involved. On a DM-started run, the brief also requests eval coverage in `<skill-dir>/evals/cases.yaml` for each consumer-visible defect in a file-set skill, unless a committed criterion already covers it. Coverage is a criterion on the case whose ask shows the defect, or a new case when every committed ask misses it (`evals/README.md` § Design). Revive that same writer for later rounds of the run, per **Native delegation**. When the round has only tool defects and false findings, skip the dispatch. **Done when** every text issue maps to an edit in the writer's yield and `bun run cfcli -- eval validate <skill-dir>` passes for each touched skill.
5. **Continue.** Report the round in a few lines: each finding with its verdict and each fix by file. A friction-started run then resumes the job on the revised text. A DM-started run returns to step 2 with fresh subagents on fresh units, scaling toward the target's production shape once small units run clean (for `lint`: four to six pages per subagent). Eval-case units rerun the cases that failed plus any case the round's fixes could break, and a criterion that passed before and now fails is a finding for that round. It ends when a round's findings are all false or the DM calls it. It then finishes the target's shared steps and runs the page gate over the landed work's pages. **Done when** a friction-started run's job has resumed on the revised text, or a DM-started run has ended and the page gate over every landed unit's pages reports `ok: 0 findings`.
