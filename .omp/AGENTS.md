## Wiki access

Read from the Backup and write to `wiki/`. **Wiki access** in `user-config.md`, imported above, defines the vault root and the repo root. Before a run's first Backup or QMD search, read `docs/agents/wiki-search.md` for each route's query grammar, examples and citation mapping.

**Notion Backup.** The Backup (`CONTEXT.md`) sits under the Notion page "campaign-foundry backup" (`3f20216635ec815c9ba6dacbda0f6f1b`) and is the first source for every read. `cfcli backup` updates it on each push to `main` (`docs/notion-backup.md`), and the `git-sync` hook (`.omp/hooks/pre/git-sync.js`) fast-forwards this checkout at session start. Between them, the Backup matches `wiki/` apart from local work not yet pushed.

- **Read from the Backup.** Answer general questions, surveys of a subject and the context around a task through `xd://mcp__notion_search` scoped to the Backup root, and cite each page by the repo path its header gives. Read the fixed orientation files (`campaign-config.md`, `hot.md`, `index.md`, `log.md`) by path from `wiki/`.
- **Write to `wiki/`.** Read each page you create or edit from `wiki/` (`read`, `vault://_/` or QMD `get`) immediately before the edit, and make the edit there. The next sync overwrites any edit made in Notion. For this Campaign the Wiki takes precedence over the Second Brain.
- **QMD and `wiki/` answer what the Backup can't:** uncommitted or unpushed Wiki work (`git status --short wiki/` and `git diff --name-only @{u} -- wiki/` list it), pages outside the Shattered Sea Wiki, `raw/`, `archive/`, aliases (the `lint` Names ladder), and every read in a session whose tools lack `xd://mcp__notion_search` (Eval Runners, `omp -p` processes). The Notion MCP server is configured at user level in `~/.omp/agent/mcp.json`. Keep it there.

## Memory

The `mnemopi` backend recalls past sessions. It injects a `<memories>` block on a session's first turn and retains completed turns as episodes, so the way a correction is worded is the way it is later recalled. DM decisions from the earlier backend are stored as facts beginning `Campaign Foundry DM decision (<heading>):` and arrive through recall. The memory devices (`xd://recall`, `xd://retain`, `xd://memory_edit`) are mounted only in some sessions, so each step below that uses one runs when your system prompt lists that device and is skipped when it doesn't.

- **Follow** the injected `<memories>` block as background. A DM decision in it is standing direction, and the DM's current instruction overrides it. Check it against current repo state before acting on it.
- **Recall** through `xd://recall` before starting work on each DM request, with one specific query about its subject, and again when the task turns on a past session or prior DM decision that neither the repo nor the injected block shows. Take Canon from the Wiki and project rules from the repo.
- **Restate** each DM correction, rejection or decision back in one durable sentence that says what to do and where it applies, leaving out this task's paths, ids and values.
- **Promote** a decision that is a durable project rule to its repo owner under root `AGENTS.md` **The repo is the memory**, in the same change.
- **Maintain** recalled memories in the same run. Repair a memory that is out of date or works against the DM's goals, and one that conflicts with the repo, the DM's current instruction or another memory, where the repo and the DM win. To repair it, read `memory://<id>` whole (recall previews are clipped) and `update` it through `xd://memory_edit`, or `invalidate` or `forget` it.
- **Write** only durable memories: facts, decisions and lessons that hold beyond this task and have no repo home, such as a tool quirk or where something lives. Save one through `xd://retain` or `learn` once a `recall` shows it is not yet stored, and correct a near-match with `memory_edit` instead. Keep task progress, pending work, session state and one-off values in the conversation, todos or `context_notes`. Set `scope: "global"` only for a lesson true in every project.
- **Brief** each subagent with the memories bearing on its slice: it inherits the parent's first-turn block and recalls nothing for its own slice.

## Native delegation

Delegate through native `task` (`context` + `tasks[]`) or eval `agent()`/`workpool()`. All subagent work stays inside this omp session. Give each item the `effort` (`lo`/`med`/`hi`) and the model (below) its work needs.

**Split by domain.** Related work in a domain other than the run's own task, such as code or docs behind an instruction change or stale instructions behind a code change, goes to the agent fit for that domain (selection below) with a brief complete enough to finish it: code to `coder`, agent-facing text to `skill-writer`. The run itself stays on its task. The top-level session dispatches that work, the errors **Fix on sight** routes included. A subagent records the friction behind that work in its friction report.

**Route friction.** Friction reaches you in two ways: the report lines closing each subagent return, and friction you meet yourself. A `task`, `wait` or `proc` result ends on `Model: <model>` (`, fallback` when one ran), the authority for which model produced that result. An immediate spawn acknowledgement precedes it. A report's `Model:` line is the agent's own account, the authority for the fallback history behind it. When any line is a `Gap:` line or a `Friction:` line other than `Friction: none`, start a friction-started `skill://dogfood` run: at once for your own lines, and once the batch has returned for reported ones. It triages the lines as evidence and dispatches your own `skill-writer` with every issue and the finished `history://` transcripts to diagnose the root issue from, then dispatches each `coder` request the writer returns, while you keep to your task. A subagent orchestrating its own workers passes their lines up in its return instead.

Give writers disjoint files and pass briefs and artifact paths explicitly. Set `isolated: true` when parallel writers may touch the same files or a change needs review before it is merged. Message a worker only with work (**Message with work**), and steer a running worker with a new instruction. Place each follow-up by context use, reasoning quality and token cost together. **Revive** the idle or parked agent that holds the context when the work builds on files it read and decisions it made: it pays only for the new instruction, where a fresh agent pays for a brief and every re-read. A worker whose result names a next step it could have taken is revived with the instruction to take it; after two such revivals on one task, read its `history://` transcript for the blocker before sending more. Before re-briefing an agent or fixing the skill it ran, check what it actually did (tool errors, cost, friction) with `skill://oh-my-pi-session-history`. **Dispatch fresh**, with a distilled brief, when the work is unrelated or fits a different specialist, and for each alternative approach to the same work. Stale context costs every turn and biases reasoning. A near-full context or a slice that must run in parallel also calls for a fresh agent: compaction degrades reasoning, and a clean start costs less over a long job.

Subagents share one worktree, so they use read-only git (`status`, `diff`, `log`, `show`) alone, plus `git mv` where the ingest archive step calls for it. To keep a baseline, save `git diff` to a file. Committing and every other change to git state is the top-level agent's job.

Select an agent by its responsibility:

- `skill-writer` (`@SKILL-WRITER`) authors every change to agent skills and every large or novel change to other agent-facing text: `.omp/agents/`, `AGENTS.md`, runbooks and pointers, plus a skill's eval cases in `evals/cases.yaml` whenever they are authored or extended. It writes agent-facing text and configuration only, and returns each code change its work needs as a dispatch request for `coder`. The orchestrator writes its briefs, owns acceptance criteria, Wiki and integration, and leaves those files to it. The writer diagnoses past each brief and fixes the contributing factors it finds in the same patch (`.omp/agents/skill-writer.md` step 1). Briefs leave the writer's own verification on, and the orchestrator reruns those checks only as acceptance. When the defect was observed in a run, wait until every ingest subagent in that batch has finished, then pass all of their finished `history://` transcripts together so the writer sees the issues directly.
- `coder` (`@CODER`) makes every code change: `src/`, `scripts/`, `evals/` code, tests and `python/`, with the configuration and dependencies they need. Brief one narrow change per dispatch with its target files, the change and the acceptance it must show; it proves the change with the targeted test that fails before and passes after, or the one command the change needs, and runs broader checks only for a cross-cutting change, since the orchestrator runs the full gates before commit.
- `test-subject` (`@TEST-SUBJECT`) runs each eval case, `smart-test-subject` (`@SMART-TEST-SUBJECT`) runs a case marked `subject: smart`, and `prose-grader` (`@PROSE-GRADER`) grades rubrics independently; all are native `task` dispatches whose frontmatter `tools:` is read-only except Runner `bash` for diagnostic CLI, batched per `skill://dogfood` `references/evals.md`.
- `creative-writer` (`@CREATIVE-WRITER`) takes Seeds, Story drafts and other explicit creative-writing dispatches outside skill evals.
- `persona` (`@PERSONA`) plays exactly one NPC in a Simulation, dispatched only by `simulate-npcs`.
- `transcript-reader` (`@TRANSCRIPT-READER`) reads Transcript chunks and verify ranges into Session Ledger files, dispatched by the top-level session as `ingest` `references/transcript.md` sets out.
- `linter` (`@LINTER`, Luna falling back to `zai/glm-5.3-flash`) makes every lint repair of a finished file, a Wiki page or an agent-facing file, one file per dispatch (root `AGENTS.md` **Gate scope**, ADR 0045), and returns its final check output. Brief it with that one file path, plus the check command when the path leaves it unclear. It hands back any repair that needs another file.

**Model choice.** Claude Opus 5.5 is reserved for writing skills and agent instructions (`skill-writer`) and orchestration, and GPT-6.1 Sol writes code (`coder`). The DM's provider tiers set the models for each role and fallback chain. Anthropic Opus 5.5 carries the intelligence-critical work. Its budget is kept off routine runs. `zai/glm-5.3` is the de facto high-level creative and default tier. `zai/glm-5.3-flash` handles quick, mechanical work and test subjects. xai Grok takes well-scoped generalist work. The plentiful Codex-subscription Luna quota covers routine, judgement-free tasks (commit messages, memory titles, vision descriptions, transcript chunks, single-file lint repair, test subjects) on a tight leash: each brief is extremely tightly scoped, with clear criteria and acceptance. Luna never takes repo plans, decisions or skill writing. A dispatch runs on its agent's model: `task.agentModelOverrides.<agent>`, else the agent's frontmatter `model`, whose `@ROLE` resolves through `modelRoles` in user `~/.omp/agent/config.yml`. Roles hotlink to a small concrete base through `@` aliases: `slow`, `advisor` and `SKILL-WRITER` → `@plan`, `vision` → `@commit`, `memory` → `@TEST-SUBJECT`, `PERSONA` → `@default`, `SMART-TEST-SUBJECT` → `@task`. Changing a base changes each alias of it. Each role has a `retry.fallbackChains.<ROLE>` chain there that moves a rate-limited or quota-dead primary across providers, stepping down these tiers and splitting usage across the DM's providers (`usageAwareFallback`). OpenAI selectors never appear in a decision-class chain (`plan`, `slow`, `advisor`, `skill-author`, `SKILL-WRITER`), and GitHub Copilot selectors, whose quota is scarce and unreliable, sit mid-chain only, never as a chain's last stop or sole entry. That fallback is the DM's policy, so keep dispatching as normal. `task` items and eval `agent()` take no `model`, so the agent you dispatch sets it. When a batch needs another model, set `task.agentModelOverrides.<agent>` in `.omp/config.yml` to a role alias (`@ROLE`) or an ordered list of selectors before dispatching it (the next launch reads it without a restart), and remove that entry once the batch returns. An override set to one `provider/model` selector falls back only along the `default` chain. Give each item the cheapest model capable of its work:

- **`zai/glm-5.3-flash`** whenever it can do the work: tightly scoped, mechanical or well-briefed runs. Exploration runs here on `scout`, through the `@smol` role.
- **`zai/glm-5.3`** when the item needs more. Creative drafting and session material run here, as do lint slices, Print-grade prose and investigation. The plain `task` agent runs it, through the `@task` role.

Choose the models for the roles below from evidence, gathered through `skill://model-evidence`. It gives the source for each question and the rule for when a provider counts as available.

- **Test subjects** in `dogfood` runs and evals: they alternate freely between GLM and Codex as usage allows. `@TEST-SUBJECT` pins Codex GPT-6-luna with a GLM-5.3-flash chain, and `usageAwareFallback` does the moving. Either way the model is the cheapest and fastest realistically capable of the task. A weak model exposes unclear instructions that a strong one silently compensates for.
- **Graders** (`prose-grader`): a model from a vendor outside every subject they grade. When `@PROSE-GRADER` shares the vendor of a subject's `Model:` line, choose another grader and set it for that batch. The Benchmark Council is the exception by design: it grades on the models under test (ADR 0038).
- **Benchmark seats** (`model` and `thinking-level` in each `bench-runner-<family>` and `bench-grader-<family>` definition, identical in the pair): the best reasonable model and reasoning effort per family with confirmed usage. Fable is never seated.

Preserve each completion's model selector, identity and thinking level where observed, and pair only matching identities and thinking levels.

Delegation stays native, except description trigger checks: those are read-only `omp -p` processes whose commands `skill-creator` `references/description-evals.md` documents.

## Tools

- **Internal first.** Use the harness's own tools where one exists, such as the mounted LSP, judge and QMD devices, and this repo's `cfcli` commands for the rest. Search with the `grep` and `glob` tools and read with `read`, since the shell blocks `grep`, `rg`, `cat`, `head` and `tail`. Run the `omp` binary only for the isolated `omp -p` processes a skill names.
- **Read whole files.** Each `read` returns one window: 300 lines with no selector, and at most 3,000 with a range such as `page.md:1-3000`. A bare read of code shows declarations only. A long result from `read` or any other tool keeps its head and tail, and saves the full window to the `artifact://<id>` its footer names, which you read by range like a file. The whole file is read once you have followed every footer (`Use :N to continue`, `Read artifact://<id>`, the ranges it names to re-read) and none remains. An `edit` anchors only to lines a `read` displayed in full: before replacing or deleting a block, read its exact range (`file.ts:218-339`) and edit with that read's tag.
- **Read `:raw`** (`page.md:raw`, `page.md:40-60:raw`) when exact text matters: frontmatter, a passage you quote or copy elsewhere, and text you compare with a source. Raw output has no line numbers or `#TAG`, so take an edit's tag from a plain `read` or `grep` of the lines you change.
- **TypeScript diagnostics.** Edits don't report them, so request `lsp` diagnostics on touched TypeScript before reporting code complete.
- **Lint reports** come from `bun run lint [agents|prose|code] [paths…]` (default: changed and untracked files). `bun run fix` applies safe fixes.
- **Library docs** come from Context7 (`skill://context7-mcp`) whenever code touches a library, framework, SDK, CLI or API, even a familiar one such as Bun, Vale or Foundry VTT, and code-writing subagents' briefs say the same.
- **Judge** bounded classification, yes/no or ranking over a small state with eval `judge`: read `xd://eval/judge` once, batch independent questions over the same evidence into one call and use `judge_batch` for multiple states. Send only the evidence the criteria need; a failed judge item is a tool failure, so inspect `item.error` before concluding.
- **Extend with TypeSafe** beyond omp's built-in Jev tools, and use those tools first. Eval `judge` and `judge_batch` answer typed questions over a state inside this session's kernel, and judged TTSR rules ask one Noul of each completed output and deliver a yes as a warning. When the work needs more, read `skill://typesafe-ai` and the live docs it links, unprompted. Its patterns cover composed judgements, such as reranking and confidence gates. `cfcli` commands, `src/`, tests and eval scripts run outside the session, so they call Jev through TypeSafe's JavaScript SDK (`bun add`) or HTTP API, which return the model version and token `usage` for reproducible runs. That code reads `TYPESAFE_API_KEY`; when it is unset, report it to the DM as the missing prerequisite.
- **Grade** Narration and other authored prose with `prose-grader`, dispatched as in `skill://dogfood` `references/evals.md`: it reads the writing, which Jev does not. Execution, diffs, isolation and Checks stay with the orchestrator.
- **Verify from command output.** Check generated pages, such as the `cfcli eval description-review` HTML, from the command's own output, and open a browser only when the DM asks for it.
- **Track goals.** At the start of a run, the top-level session turns each goal and acceptance criterion of the DM's ask into a `todo` item. It marks an item done once verified or blocked once reported, and finishes only when none is left pending. Subagents have no `todo`: scope each brief tightly enough that its Target, Change and Acceptance are the whole plan.
- **Long work.** Keep `context_notes` current with the goal, decisions, touched paths and next step, and call `new_context` at phase boundaries.
- **Waiting.** Results from background `bash` jobs, `task` and eval subagents and messages arrive on their own, so carry on with other work meanwhile. When only they can unblock you, call `wait` (in eval, `wait(handles)`). It returns on the next result or message, or after a short window while workers still run, so call it again until what you need arrives. When it reports nothing to wait for, an orchestrator messages the worker that owns what it needs with the instruction, which wakes it, then calls `wait`. A worker reports the blocker to its parent (**Message with work**). Start a service with `bash` `name` and `ready`, and give a command that runs past the 300 s default a `timeout` that covers it. Read `proc://<id>` or `agent://<id>` once, when a status report needs it.

## Skill tooling

Skill improvement, change and eval runs go through `skill://dogfood` (ADR 0034), against the case contract in `evals/README.md`. The omp-native skills below are the invocation points:

- **Improve, change or eval a skill.** Read `skill://dogfood` before changing an existing skill, agent definition or process, or running its committed `evals/cases.yaml`.
- **Create a skill.** Read `skill://skill-creator` before creating a new skill.
- **Benchmark Narration.** Read `skill://dnd-benchmark` before ranking Matrix families or presenting the leaderboard.

Project skills live in `.omp/skills/` and `.agents/skills/`; where both hold a skill, the `.omp/` copy is the source of truth. `manage_skill` holds the DM's cross-project procedures; project skills, rules and decisions live in the repo.

## Configuration

**Extend omp.** When the DM asks to change what this repo or the harness can do (a tool, hook, rule, skill, setting, agent, MCP server, extension or plugin), read `skill://extending-omp` first and follow it to build the change.

Native agent definitions live in `.omp/agents/`, with descriptive names and narrow responsibilities. Add a project agent for a new job rather than overriding a bundled one. Before changing configuration, inspect the effective settings and agent definitions and preserve unrelated overrides. Keep approvals and providers as configured when making a task run.

This file imports the shared root instructions because native context shadows a root `AGENTS.md` at the same directory depth. Keep project rules in that root file and tool, agent and configuration mechanics here.
