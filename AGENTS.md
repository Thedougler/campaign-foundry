# Campaign Foundry

Campaign Foundry is an LLM Wiki for a live D&D table: the product is the Campaign content (Narration, NPCs, Locations, Creatures, Items, Sessions), written as an author writes a book, and all code (CLI, Checks, evals, Push) serves that writing, so judge every piece of work by whether the content gets better.

## Schema

Layers:

- **Raw**: `raw/` holds files awaiting Ingest; `archive/` keeps them once ingested, as provenance.
- **Wiki**: `wiki/`, the compounding Canon. The DM edits it and has final say. The Agent does the bookkeeping. Each page kind's template in `wiki/templates/` states its required properties and sections. Each Campaign folder has a generated `index.md` catalog, an append-only `log.md` and a `hot.md`. Read `docs/wiki-layout.md` before creating or moving a page.
- **Backup**: the remote, managed Notion database of `main`'s Wiki and skills (`docs/notion-backup.md`). Agents read from it first and write to `wiki/`, which stays the record (`.omp/AGENTS.md` § Wiki access).
- **Schema**: this file, `CONTEXT.md` (the glossary, imported at the end of this file: use its term for every domain concept) and `docs/adr/` (decisions: read those touching an area before changing it).

Operations:

- **Ingest** digests Raw, or D&D Beyond PC updates, into the Wiki through the `ingest` skill (`pull-pcs` for PCs). Done when every statement sits on its page, the file is in `archive/`, and `hot.md` is current.
- **Query** answers from the Wiki through the `query` skill, reading the Backup first (`.omp/AGENTS.md` § Wiki access). Done when every fact cites a page read this run and a keeper answer is filed back.
- **Lint** repairs Wiki mechanics through the `lint` skill, one slice of pages per run. `bun run cf -- check` is the one gate. Skills guide judgment, and Vale and the narration layer define the rules. Done when the slice's page gate reports `ok: 0 findings`.

## Sourcing

Campaign content follows the 2024 D&D 5e rules. Reuse before inventing: for a rules figure or new content (a Creature, Item, Spell, NPC, Location, adventure idea), take it from the first source that fits the DM's intent:

1. **The Wiki**: its House Rules, homebrew and everything else recorded there are Canon.
2. **The SRD**: `dnd5e-srd-api` for spell text, stat blocks, class tables, items and rules text.
3. Search **the web** for official content outside the SRD, then homebrew and published material to co-opt. Search with `web_search`. Fetch a result with `read` on its URL.
4. **Novel content**, only when nothing found fits, inspired by the closest material the search turned up.

Foundry is never a source. Retell every source in fresh words: a book that copies its inspiration is a bad book.

## Content stance

Content rating and themes come from the DM. Match the rating of what the DM writes and asks for, in your own words. An R-rated ask gets R-rated fiction through every draft and brief: people in the World swear where it fits, and violence and cruelty are shown on the page. It is never softened to PG-13. Speak to the DM as the adult they are. Themes the DM names (dark, broken, grim) keep their full strength. This is fiction among friends, and the DM has final authority. Everything is allowed except the Campaign's Lines and Veils, which the Players submit and the DM reviews, recorded in its `campaign-config.md`. Villains are evil and do evil on the page, so that good can triumph over them.

## In-world voice

Characters live in the fiction, and the rules engine stays outside it. Everything a character says, knows or thinks, and every line of Narration or Story prose, uses words the World itself would use. Rules terms such as Legendary Resistance, hit points, spell slots, saving throws, DCs, Actions, levels and Challenge Ratings stay in statblocks and DM-layer notes. When a mechanic matters to the fiction, write what the people in the scene would perceive. A Legendary Resistance becomes a spell that should have dropped him and didn't. Lost hit points become blood and ragged breath.

## Orient

Read order at the start of every run: `user-config.md` (imported at the end of this file) before any Wiki operation; in a Campaign, its `campaign-config.md`; then the Campaign's `hot.md` (orientation, not evidence), the Campaign folder's `index.md`, the last ten `log.md` entries, then task pages. Every search for context, from a survey of the task's subjects to one name lookup, starts with the Notion MCP, `xd://mcp__notion_search`: the Second Brain for the DM's own context, the Backup for the Wiki. Read and write the Wiki as `.omp/AGENTS.md` § Wiki access sets out.

For creative work (raw ideas, Stories, NPCs played in Simulation, Session ideas), read `docs/creative-process.md`: it maps the stages, agents and the file that defines each rule.

## Working rules

- **Install before building.** Before building a tool, search the web for an established one that does the job (a package, CLI, skill or script), then download, install and co-opt it, adding packages with `bun add`. Write custom code only for what the co-opted tools leave undone: rebuilding a tool that exists is a critical failure. Python code goes in `python/` under uv: add its dependencies with `uv add`, run it through the `py:*` scripts in `package.json`.
- **Programmable judgment.** A script decides only what is deterministic over its input: chunking, counting, hashing, gates, logs, indexes, file lists and literal existence checks. Relevance, meaning, membership and support over natural-language input are judgements. The agent makes them by reading pages and files it finds through the `grep` and `glob` tools or Backup and QMD search (`.omp/AGENTS.md` § Wiki access), or with eval `judge` and `judge_batch` for a quick bounded call (a pick from a set, a yes or no, a degree, a ranking). Code keeps the workflow and the policy, and its output is diagnostic input the agent reads before deciding, including the answers and probabilities a `cf` command gets from Jev. For what the harness judge cannot do, read the `typesafe-ai` skill and build the judgment with TypeSafe without waiting to be asked. In omp, **Tools** in `.omp/AGENTS.md` sets out which side of that line a need is on.
- **Rules without exceptions.** Every rule applies everywhere. When a case needs a carve-out, the DM's own requests included, redefine the rule's terms until the case falls inside them (a PC's backstory counts as revealed once its Player writes it), and record the new definition in the file that states the rule.
- **Scope is the ask.** Execute exactly the task the DM names and only what serves that goal. Serving the goal always includes searching the web for added context and finding and applying the best practices and optimizations the DM left unstated, and each repair **Fix on sight** calls for serves it too, with its files counted as named by the ask. Keep edits to what the ask names, including a file read by another harness or agent only if the DM names it.
- **Fix on sight.** This is a living repo under heavy development, and the agents' experience of working in it comes first. Own every error you meet mid-task at once, without asking leave and without reporting it as a finding. Repair it in the same run, or hand it to the agent best fit for it (`skill-writer` for agent-facing text) so you stay on your own task. An agent without `task` returns that hand-off as a dispatch request (**Nested dispatch**). An error is anything that works against the project's stated goals: broken code, stale or broken agent-facing text (`AGENTS.md` files, skills, agent definitions), and the friction an agent hits, from a step or workflow that confuses you to a subagent doing misdirected, redundant or rabbit-holed work. Rewrite a confusing step so the next agent runs it cleanly, and put to the DM only a step whose intended meaning the evidence leaves open (**Ask on ambiguity**). Correct a wasting subagent at once: re-brief, redirect or stop it. A harness change the DM made is intent, and you proceed with it as made (**User edits are intentional**).
- **Behaviour beats labels.** Treat a document's classification of a thing as a claim to check against what the thing actually does before acting on the label. Check the pages it creates and the commands it runs, along with any files it touches. Where a document and observable behaviour conflict, behaviour wins: repair the false document in the same run and record the repair where it belongs.
- **Ask on ambiguity.** Decide what the repo, tools or Wiki can settle from that evidence: state the decision and its one-line evidence, then execute. When the DM uses a term you don't understand, read `skill://domain-modeling` and resolve the term as it directs, then read the files the term bears on and edit each one its resolved meaning changes. When an agent-facing instruction is unclear or contradicts another, ask the DM. The top-level session asks one batched question that quotes each such instruction and proposes simpler wording. A subagent puts its question in its return for the top-level session to ask.
- **The repo is the memory.** Record every durable fact, preference or decision in the repo (terms in `CONTEXT.md`, decisions in `docs/adr/`, working rules here), not in harness memory files.
- **Intent is not the build.** `docs/intent/` records what earlier skills and templates were meant to do. Build every v2 from scratch under its README.
- **Less is more.** Every piece of agent-facing text (`AGENTS.md` files, skills, agent definitions, rules, hook-injected text, runbooks, prompts) does its job with as few instructions as it can. The default move on every change is to refine and consolidate what exists, adding a new rule only when better existing text cannot meet the need. Remove conflicting, useless and repeated text, and rewrite the rest in clear, concise, direct and flexible wording. Prefer one general rule that applies everywhere to ten narrow ones, and make each rule only as specific as it must be: a rule that over-applies shows in the next run and gets tuned, while nobody sees the cases a too-narrow rule misses. Read `writing-for-agents` before writing any of it, and follow it.
- **Skills, templates and lint move together.** A change to a skill or a template reviews its related skills, templates and lint rules in the same change. For a skill, that is the template of each page kind it writes plus each skill it hands off to or points at. Templates pair with every skill that writes their page kind and with the `cf check` layers and rules that enforce that page kind. Lint reads page shape (sections, optional markers, callouts) from the template itself. The template is the source of truth, and a template edit doesn't need a matching code edit. Update each related file that no longer agrees. Done when the change's report lists every related file with its edit or "agrees".
- **Print grade.** Every line of Campaign content you write or touch reads as polished, professional prose that a published adventure would print. A clean gate is the floor, never the proof. Odd, stilted or inverted wording on a page you touch, older lines included, is rewritten in the same run.
- **Flesh out thin pages.** A Wiki page you meet in any task that reads thin or generic gets a `flesh-out` pass in the same run, without asking leave. Weave its new detail first from the Wiki material already tied to its subject, and invent only what that material leaves open. Any detail that conflicts with no Canon (`CONTEXT.md` **Canon**) goes straight onto the page.
- **Zero findings.** The gate's rules are correct, and every `bun run cf -- check` finding binds, whether from Vale (`ai-tells` and every other rule), Harper, cspell, markdownlint, remark-lint or the narration layer, warnings as much as errors. Fix every finding on a page you touch in the same run by rewriting the flagged text. For a flagged name, follow the Names ladder in `skill://lint`. Rule files and layer settings change in two cases only. When a rule contradicts what the exemplar DMs do (ADR 0029), the rule is wrong and changes. For a rare, obvious false match on literal campaign meaning (a ship that is literally a ship), the DM may confirm switching that Vale rule off in `.vale.ini`, asked as **Ask on ambiguity** sets out. Until the DM confirms, rewrite the flagged text like any other finding. The gate passes at `ok: 0 findings` only, so exit 0 with warnings left is a failing gate. Work ends only when no finding remains, or when each one left has failed twice and the report quotes it for the DM (`skill://lint` step 7).
- **Gate scope.** Check each page as you finish editing it, and repair every finding the check reports before you open the next page. A successful `write`, `edit` or `apply_patch` to a page under `wiki/` returns that check: the `wiki-check` hook in `.omp/hooks/post/` appends the findings of the read-only `bun run cf -- check --json "<page>"` to the tool result. The check returned by a page's latest edit is that page's check, and it meets any skill step that says to check the page. Run `bun run cf -- check "<page>"` yourself when that edit returned no check, a capped list, an error or a timeout, or when the page last changed by another route (`--fix`, `cf index`, a shell command, a vault named by `--vault`). The hook only reports; every repair is yours, by the rules above and `skill://lint` for the gate's layers. Each run then passes its **page gate**: `bun run cf -- check` given the path of every page the run was handed or touched, at `ok: 0 findings`, after its last edit. A check over a list of pages evaluates only those pages and reads the rest of the Wiki as context for links, orphans and shared lines, so a later edit to one page can change another page's findings. The **full gate**, `bun run cf -- check` with no paths, evaluates every page and belongs to the top-level agent, which hands the pages it flags to `lint` runs, a slice each (`skill://lint`, Whole Wiki).
- **Message with work.** Every message from one agent to another gives an instruction or a deliverable. A hand-off that a brief or contract defines qualifies, such as a gate finding sent to the writer editing that page or a failing result sent back with its failure, and so does the orchestrator's next instruction to a worker. Otherwise a subagent works its own slice and reports in its return, and its parent follows progress by reading `agent://` and `proc://`. A shared file (`log.md`, `hot.md`, a page another run also edits) is edited without asking: re-read it just before the edit and keep every line you are not changing.
- **Nested dispatch.** A subagent may dispatch its own subagents (`task` or an eval `agent()`), up to `task.maxRecursionDepth: 3` in `.omp/config.yml`. Transcript ingest still runs as flat stages from the top-level session (ADR 0021): each stage returns the dispatches it needs, and the top-level session makes them. An agent without the `task` tool (one at the depth limit, or a native agent whose definition doesn't declare `spawns`) does any plain `task` part itself and returns each other dispatch it needs as a request with its exact task text. Its caller dispatches each request it judges fit, then resumes the requester by message with the results.
- **Independent audit.** An audit (`skill://audit`) always runs in a fresh subagent, never in the agent that did the work it audits. The agent that did the work dispatches it, save an ingest subagent, which returns its audit as a dispatch request (`skill://ingest` step 13).
- **Skill verification.** A skill or other agent-facing document is done when its body matches the brief. A new eval case, in a new or an existing `evals/cases.yaml`, comes only from a `skill://dogfood` run the DM starts to improve that skill, content skills included. Committed cases stay. Instruction-only changes don't need software tests. Test executable code at its public interfaces.
- **Evals.** Read `evals/README.md` before authoring, running or grading evals or processing home-Session feedback. It defines the recipe, Shattered Sea grounding and the Runner's read-only access. An Eval reports failures. Only a Hillclimb edits skill text.
- **Prior iterations.** Facts come from this repo, the installed tools and the DM. Earlier iterations of this project are a mine for ideas, code and lore: start from `docs/research/prior-iterations/README.md`, which lists each repo with its findings file. The live Wiki is Canon, mined lore enters it retold, and this repo's code and skills are built here with prior ones as reference.
- **Models in configuration.** Model selection is set in configured model roles and native agent frontmatter, and the orchestrator picks each `task` item's model by `.omp/AGENTS.md` **Native delegation**. `evals/models.yaml` pins the Benchmark Matrix. Images and their models come from the `visuals` skill.
- **User edits are intentional.** When the DM changes their harness configuration (model roles, settings, `.omp/` files, agent definitions, eval pins), proceed as intended. Audit or re-validate it only when asked.
- **Commit everything.** The top-level agent's last step in a run is its commit, made once the work is checked. Stage every tracked and untracked worktree change, the DM's edits included, with `git add -A`. Then run `omp commit -c "<the task in one line>"`, which writes the message with the `commit` model role (`@commit`) and makes the commit.
- **Close completed issues.** Once an issue's acceptance criteria are met, verified and committed, close it with a brief comment citing the commit and the verification.
