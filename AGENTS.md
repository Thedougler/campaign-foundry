# Campaign Foundry

Campaign Foundry is an LLM Wiki for a live D&D table, and its one goal is the best-quality, most fun Sessions for the DM's Campaign, filled with professional-grade content the Players find engaging, interesting, memorable and fun. That Campaign content (Narration, NPCs, Locations, Creatures, Items, Sessions) is the product, written as an author writes a book. Judge every piece of work by whether it makes the Sessions better, and fix whatever works against that goal.

Evals and their criteria codify the DM's intent durably and steer the project's development, so revise them whenever that intent changes: a wrong criterion sends the work the wrong way and wastes time and tokens. Code serves the agents. It automates every deterministic step (the CLI, Checks and Push), so agents spend as much of their reasoning budget as they can on the subjective judgement and creative work of the task at hand.

## Schema

Layers:

- **Raw**: `raw/` holds files awaiting Ingest; `archive/` keeps them once ingested, as provenance.
- **Wiki**: `wiki/`, the compounding Canon. The DM edits it and has final say. The Agent does the bookkeeping. Each page kind's template in `wiki/templates/` states its required properties and sections. Each Campaign folder has a generated `index.md` catalog, an append-only `log.md` and a `hot.md`. Read `docs/wiki-layout.md` before creating or moving a page.
- **Backup**: the remote, managed Notion database of `main`'s Wiki and skills (`docs/notion-backup.md`). Agents read from it first and write to `wiki/`, which stays the record (`.omp/AGENTS.md` § Wiki access).
- **Schema**: this file, `CONTEXT.md` (the glossary, imported at the end of this file: use its term for every domain concept) and `docs/adr/` (decisions: read those touching an area before changing it).

Operations:

- **Ingest** digests Raw, or D&D Beyond PC updates, into the Wiki through the `ingest` skill (`pull-pcs` for PCs). Done when every statement sits on its page, the file is in `archive/`, and `hot.md` is current.
- **Query** answers from the Wiki through the `query` skill, reading the Backup first (`.omp/AGENTS.md` § Wiki access). Done when every fact cites a page read this run and a keeper answer is filed back.
- **Lint** repairs Wiki mechanics through the `lint` skill, one slice of pages per run. `bun run cfcli -- check` is the one gate. Skills guide judgement, and Vale and the narration layer define the rules. Done when the slice's page gate reports `ok: 0 findings`.

## Sourcing

Campaign content follows the 2024 D&D 5e rules. Reuse before inventing: for a rules figure or new content (a Creature, Item, Spell, NPC, Location, adventure idea), take it from the first source that fits the DM's intent:

1. **The Wiki**: its House Rules, homebrew and everything else recorded there are Canon.
2. **The SRD**: `dnd5e-srd-api` for spell text, stat blocks, class tables, items and rules text.
3. Search **the web** for official content outside the SRD, then homebrew and published material to co-opt. Search with `web_search`. Fetch a result with `read` on its URL.
4. **Novel content**, only when nothing found fits, inspired by the closest material the search turned up.

Foundry is never a source. Retell every source in fresh words: a book that copies its inspiration is a bad book.

A page's optional `inspired_by` property names what the DM drew it from, such as `inspired_by: "Aleksander Anderson from the Hellsing anime"`. Set it only where the DM's own words state that inspiration, spoken to the Agent or found in Raw being ingested. Before building on a page that has one, understand the work it names. Read it where the repo has it, in the Wiki, QMD or a cached note at `.cache/inspired-by/<page-slug>.md` (QMD collection `inspired-by`), else fetch its URL or search with `web_search`, until you can state the DM's concept in a sentence. Save what a fetch or search taught you to that note for later runs: the cache is gitignored and never enters the Wiki. Then carry its vibes and themes onto the page, retold in fresh words.

## Content stance

Content rating and themes come from the DM. Match the rating of what the DM writes and asks for, in your own words. An R-rated ask gets R-rated fiction through every draft and brief: people in the World swear where it fits, and violence and cruelty are shown on the page. It is never softened to PG-13. Speak to the DM as the adult they are. Themes the DM names (dark, broken, grim) keep their full strength. This is fiction among friends, and the DM has final authority. Everything is allowed except the Campaign's Lines and Veils, which the Players submit and the DM reviews, recorded in its `campaign-config.md`. Villains are evil and do evil on the page, so that good can triumph over them.

## In-world voice

Characters live in the fiction, and the rules engine stays outside it. Everything a character says, knows or thinks, and every line of Narration or Story prose, uses words the World itself would use. Rules terms such as Legendary Resistance, hit points, spell slots, saving throws, DCs, Actions, levels and Challenge Ratings stay in statblocks and DM-layer notes. When a mechanic matters to the fiction, write what the people in the scene would perceive. A Legendary Resistance becomes a spell that should have dropped him and didn't. Lost hit points become blood and ragged breath.

## Orient

Read order at the start of every run: `user-config.md` (imported at the end of this file) before any Wiki operation; in a Campaign, its `campaign-config.md`; then the Campaign's `hot.md` (orientation, not evidence), the Campaign folder's `index.md`, the last ten `log.md` entries, then task pages. Every search for context, from a survey of the task's subjects to one name lookup, starts with the Notion MCP, `xd://mcp__notion_search`: the Second Brain for the DM's own context, the Backup for the Wiki. Read and write the Wiki as `.omp/AGENTS.md` § Wiki access sets out.

For creative work (raw ideas, Stories, NPCs played in Simulation, Session ideas), read `docs/creative-process.md`: it maps the stages, agents and the file that defines each rule.

## Working rules

- **Install before building.** Before building a tool, search the web for an established one that does the job (a package, CLI, skill or script), then download, install and co-opt it, adding packages with `bun add`. Write custom code only for what the co-opted tools leave undone: rebuilding a tool that exists is a critical failure. Python code goes in `python/` under uv: add its dependencies with `uv add`, run it through the `py:*` scripts in `package.json`.
- **Programmable judgement.** A script decides only what is deterministic over its input: chunking, counting, hashing, gates, logs, indexes, file lists and literal existence checks. Relevance, meaning, membership and support over natural-language input are judgements. The agent makes them by reading pages and files it finds through the `grep` and `glob` tools or Backup and QMD search (`.omp/AGENTS.md` § Wiki access), or with eval `judge` and `judge_batch` for a quick bounded call (a pick from a set, a yes or no, a degree, a ranking). Code keeps the workflow and the policy, and its output is diagnostic input the agent reads before deciding, including the answers and probabilities a `cfcli` command gets from Jev. For what the harness judge cannot do, read the `typesafe-ai` skill and build the judgement with TypeSafe without waiting to be asked. **Tools** in `.omp/AGENTS.md` places each omp need on that line.
- **Rules without exceptions.** Every rule applies everywhere. When a case needs a carve-out, the DM's own requests included, redefine the rule's terms until the case falls inside them (a PC's backstory counts as revealed once its Player writes it), and record the new definition in the file that states the rule.
- **Scope is the ask.** Execute exactly the task the DM names, as the smallest change that meets its acceptance criteria. Serving the goal includes searching the web for added context, doing each part the established best way where the DM leaves the method unstated, and each repair **Fix on sight** calls for, with its files counted as named by the ask. Write plain code for the cases its callers produce, built from existing helpers. Validate input where it enters the system; past that point, trust internal code and let errors propagate. Add an abstraction, option, fallback or check when the ask or a present caller needs it. Results propose further work only within this bound. Keep edits to what the ask names, including a file read by another harness or agent only if the DM names it.
- **Fix on sight.** This repo is under heavy development, and the agents' experience of working in it comes first. Own every error you meet mid-task without asking leave or reporting it as a finding: repair it in the same run, or hand it to the best-fit agent (`skill-writer` for agent-facing text). An agent without `task` returns that hand-off as a dispatch request (**Nested dispatch**). Any friction counts as an error, from broken code or stale agent-facing text to a confusing step or a subagent doing misdirected work. Treat a workaround that complicates your task (a hack, shim, special case, manual step or detour around something broken or missing) the same way: first find the correct approach in the repo's docs and ADRs or through Context7 and the web, then repair the cause so the workaround is gone. Rewrite a confusing step so the next agent runs it cleanly, and ask the DM only about a step whose meaning the evidence leaves open (**Ask on ambiguity**). Re-brief, redirect or stop a wasting subagent at once. A harness change the DM made is intent (**User edits are intentional**).
- **Fast feedback.** Fix slow tests and tooling as you meet them. A full test run over about five minutes is a **Fix on sight** defect: parallelise, prune, cache or drop redundant coverage until it fits. Kill a run that is clearly broken or wedged as soon as it shows, then repair its cause.
- **Proactive laziness.** Stay lazy about everything outside your objective so the objective gets your full effort, never lower quality. When you finish complex, objective, deterministic work that called for neither judgement nor reasoning, automate it with a command, script or stated fact so the next agent repeats none of it (trail clearing). Speed bumps you meet are **Fix on sight** defects.
- **Behaviour beats labels.** Treat a document's classification of a thing as a claim to check against what the thing actually does before acting on the label. Check the pages it creates and the commands it runs, along with any files it touches. Where a document and observable behaviour conflict, behaviour wins: repair the false document in the same run and record the repair where it belongs.
- **Ask on ambiguity.** Decide what the repo, tools or Wiki can settle from that evidence: state the decision and its one-line evidence, then execute. When the DM uses a term you don't understand, read `skill://domain-modeling` and resolve the term as it directs, then read the files the term bears on and edit each one its resolved meaning changes. When an agent-facing instruction is unclear or contradicts another, ask the DM: the top-level session asks one batched question quoting each such instruction with simpler wording, and a subagent returns its question for the top-level session to ask.
- **The repo is the memory.** Record every durable fact, preference or decision in the repo (terms in `CONTEXT.md`, decisions in `docs/adr/`, working rules here), not in harness memory files.
- **Intent is not the build.** `docs/intent/` records what earlier skills and templates were meant to do. Build every v2 from scratch under its README.
- **Less is more.** Every piece of agent-facing text (`AGENTS.md` files, skills, agent definitions, rules, hook-injected text, runbooks, prompts) does its job with as few instructions as it can. Refine and consolidate what exists before adding a rule, and remove conflicting, useless and repeated text. Prefer one general rule to ten narrow ones, each only as specific as it must be: a rule that over-applies shows in the next run and gets tuned, while nobody sees the cases a too-narrow rule misses. Read `writing-for-agents` first and follow it.
- **Skills, templates and lint move together.** A change to a skill or a template reviews its related files in the same change. For a skill, those are the template of each page kind it writes and each skill it hands off to or points at. For a template, they are every skill writing its page kind and the `cfcli check` layers and rules enforcing it. Lint reads page shape from the template, the source of truth, and a template edit doesn't need a matching code edit. Update each related file that no longer agrees. Done when the change's report lists every related file with its edit or "agrees".
- **Print grade.** Every line of Campaign content you write or touch reads as polished, professional prose that a published adventure would print. A clean gate is the floor, never the proof. Odd, stilted or inverted wording on a page you touch, older lines included, is rewritten in the same run.
- **Flesh out thin pages.** A Wiki page you meet in any task that reads thin or generic gets a `flesh-out` pass in the same run, without asking leave. Weave its new detail first from the Wiki material already tied to its subject, and invent only what that material leaves open. Any detail that conflicts with no Canon (`CONTEXT.md` **Canon**) goes straight onto the page.
- **Write, then repair.** Skills and templates describe what to write in positive craft terms, and the writer drafts freely from them. Gates run on the written text, and repairing their findings is how mistakes get fixed. Each finding gives its rule and passing form, and `skill://lint/prose.md` is the repair reference to read when findings need it. When a finding traces to wording a skill or template asks for, repair that text or hand it off as **Fix on sight** sets out (ADR 0036).
- **Zero findings.** The gate's rules are correct, and every `bun run cfcli -- check` finding binds, from every layer, warnings as much as errors. Fix every finding on a page you touch in the same run by rewriting the flagged text. For a flagged name, follow the Names ladder in `skill://lint`. Rule files and layer settings change in two cases only. When a rule contradicts what the exemplar DMs do (ADR 0029), the rule is wrong and changes. For a rare, obvious false match on literal campaign meaning (a ship that is literally a ship), the DM may confirm switching that Vale rule off in `.vale.ini`, asked as **Ask on ambiguity** sets out. Until then, rewrite the flagged text. The gate passes at `ok: 0 findings` only, so exit 0 with warnings left fails. Work ends only when no finding remains, or when each one left has failed twice and the report quotes it for the DM (`skill://lint` step 7).
- **Gate scope.** Check each page as you finish editing it, and repair every finding before you open the next page. A successful `write`, `edit` or `apply_patch` to a page under `wiki/` returns that check: the `wiki-check` hook in `.omp/hooks/post/` appends the read-only `bun run cfcli -- check --json "<page>"` findings to the tool result, and that check meets any skill step that says to check the page. Run `bun run cfcli -- check "<page>"` yourself when the edit returned no check, a capped list, an error or a timeout, or when the page last changed by another route (`--fix`, `cfcli index`, a shell command, a vault named by `--vault`). The hook only reports; every repair is yours, by the rules above and `skill://lint`. Each run then passes its **page gate**: `bun run cfcli -- check` given every page the run was handed or touched, at `ok: 0 findings`, after its last edit. A check over listed pages evaluates only those and reads the rest of the Wiki as context, and editing one page can change another's findings. The **full gate**, `bun run cfcli -- check` with no paths, belongs to the top-level agent, which hands the pages it flags to `lint` runs, a slice each (`skill://lint`, Whole Wiki).
- **Message with work.** Messages run only between an orchestrator and its own workers, and nobody messages peers or broadcasts. The orchestrator coordinates every hand-off with its next instruction to a worker. It sends a gate finding or failing result back to the worker that made it, and relays whatever one worker needs from another. A worker works its own slice and puts its deliverable or blocker in its return, which reaches its parent on its own (`.omp/AGENTS.md` **Waiting**), or in one message to its parent. A shared file (`log.md`, `hot.md`, a page another run also edits) is edited without asking: re-read it just before the edit and keep every line you are not changing.
- **Nested dispatch.** A subagent does its own slice itself. Within the `task.maxRecursionDepth: 3` limit in `.omp/config.yml`, it dispatches its own subagents (`task` or an eval `agent()`) only for work inside its slice that would otherwise pull its focus, such as a large mechanical side slice or an independent part that truly runs in parallel. Splitting a small task across workers, coordinating them or repeating its parent's orchestration costs more tokens than it saves, so the subagent does that work in its own run. Transcript ingest still runs as flat stages from the top-level session (ADR 0021): each stage returns the dispatches it needs, and the top-level session makes them. An agent without the `task` tool (one at the depth limit, or a native agent whose definition doesn't declare `spawns`) does any plain `task` part itself and returns each other dispatch it needs as a request with its exact task text. Its caller dispatches each request it judges fit, then resumes the requester by message with the results.
- **Independent audit.** An audit (`skill://audit`) always runs in a fresh subagent, never in the agent that did the work it audits. The agent that did the work dispatches it, save an ingest subagent, which returns its audit as a dispatch request (`skill://ingest` step 13).
- **Skill verification.** A skill or other agent-facing document is done when its body matches the brief. A new eval case, in a new or an existing `evals/cases.yaml`, comes only from a `skill://dogfood` run the DM starts to improve that skill, content skills included. Committed cases stay. Instruction-only changes don't need software tests. Code gets the tests the ask or its acceptance criteria name, each driving behaviour a consumer relies on through a public interface.
- **Evals.** Read `evals/README.md` before authoring, running or grading evals or processing home-Session feedback. It defines the recipe, Shattered Sea grounding and the Runner's read-only access. An Eval reports failures. Every improvement or change to a skill or other agent-facing text runs through `skill://dogfood` (ADR 0034).
- **Prior iterations.** Facts come from this repo, the installed tools and the DM, and a claim about the project's history cites the git log, a file or command output. Earlier iterations of this project are a mine for ideas, code and lore: start from `docs/research/prior-iterations/README.md`, which lists each repo with its findings file. The live Wiki is Canon, mined lore enters it retold, and this repo's code and skills are built here with prior ones as reference.
- **Models in configuration.** Model selection is set in configured model roles and native agent frontmatter, and the orchestrator picks each `task` item's model by `.omp/AGENTS.md` **Native delegation**. `evals/models.yaml` pins the Benchmark Matrix. Images and their models come from the `visuals` skill.
- **User edits are intentional.** When the DM changes their harness configuration (model roles, settings, `.omp/` files, agent definitions, eval pins), proceed as intended. Audit or re-validate it only when asked.
- **Commit everything.** The top-level agent's last step in a run is its commit, made once the work is checked. Stage every tracked and untracked worktree change, the DM's edits included, with `git add -A`, then commit with `git commit` and a Conventional Commit message you write yourself.
- **Close completed issues.** Once an issue's acceptance criteria are met, verified and committed, close it with a brief comment citing the commit and the verification.
